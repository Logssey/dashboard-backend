# 보안 기능 조치 양식

시크릿·IaC·이미지는 `담당자 → 처리 상태 → 조치 내용 → 확인 결과` 순서로 표시한다.
시크릿은 기존 위치별 배정, 실제 조치 기록, 재검사, 해결 조건을 그대로 사용한다.
IaC 경로/발견 건과 이미지 발견 건은 신규 조치 기록 API를 사용한다.

## API

- `GET /api/v1/action-records/{kind}/{id}`: 현재 기록, 원래 검사 대상, 배정 가능한 관리자, 최근 50개 변경 이력.
- `PUT /api/v1/action-records/{kind}/{id}`: 담당자와 조치 진행 기록을 함께 저장.
- `GET /api/v1/action-records?area=IAC|IMAGE&assignee=ALL|ME|UNASSIGNED&page=0`: 조치 기록 목록, 30개씩 조회.
- `POST /api/v1/action-records/IMAGE/{id}/verification`: `{version, scanId}`로 조치 이후 이미지 검사 연결. 연결 이력은 내부에 보존한다.
- `kind`: `IMAGE`, `IAC_PATH`, `IAC_FINDING`. 시크릿은 지원하지 않는다. 기존 시크릿 권한 검사를 우회할 수 없다.
- 기존 IaC/이미지 변경 API와 동일하게 로그인한 `ADMIN`만 접근한다. 세션 인증과 CSRF 검사를 유지한다.
- 요청: `version`, `sourceVersion`, `assigneeUserId` (미지정은 null), `status`, `note`, `confirmed`.
- 본문 누락/잘못된 상태/존재하지 않는 담당자는 400, 로그인 없음 401, 권한 없음 403, 대상 없음 404, 버전 충돌 409.

## 기록의 의미

| 상태 | 의미 | 입력 조건 |
|---|---|---|
| NOT_STARTED | 시작 전 | 담당자 생략 가능 |
| IN_PROGRESS | 조치 중 | 담당자 필요 |
| AWAITING_CHECK | 확인 대기 | 담당자와 수행 내용 필요 |
| RECORDED | 조치 기록 완료 | 담당자, 수행 내용, 실제 수행 확인 필요 |

`RECORDED`는 담당자가 작성한 수행 기록의 마감이다. **취약점 해결, 위험 수용, 검사 통과를 의미하지 않는다.**
저장으로 reach 판정, 이미지 리뷰, IaC OPEN/FIXED/ACCEPTED, 공격 경로 OPEN/CLOSED를 바꾸지 않는다.
검사 확인 결과는 `PENDING`(검사 확인 대기), `FOUND`(다시 발견), `NOT_FOUND`(검사에서 미발견), `UNCONFIRMED`(확인 불가)를 사용한다.
이미지는 같은 서비스와 이미지 저장소에서 조치 이후 시작한 비 PR 검사를 사용자가 선택한다. SBOM 저장, SBOM/MATCH 단계 성공, 원래 탐지 도구의 실행을 확인한다. 같은 CVE·패키지·생태계가 검사 결과에 있으면 호출 불가 판정이어도 FOUND다. 선택한 이미지의 결과이며 운영 배포 여부를 의미하지 않는다.
IaC는 워커가 기록한 `checked_job_id` / `checked_run_id`로 조치 이후의 성공한 검사와 연결한다. 마지막 발견 시각으로 재검사를 추정하지 않는다. PR plan의 결과는 운영 인프라의 결과와 구분한다.
조치 기록을 변경하면 이전 결과 연결을 재사용하지 않는다. 더 최근 검사가 실패하거나 진행 중이면 과거 미발견을 현재 해결 근거로 보여주지 않는다. 레거시 기록은 새 검사 전까지 확인 대기다.
시크릿은 기존 승인 범위, 위치별 조치, 재검사 및 키 폐기·교체 조건을 유지한다. 위치 미발견만으로 대응 건을 자동 종결하지 않는다.

## 동시 수정과 내부 이력

원래 대상 행을 먼저 잠가 최초 저장 경쟁도 직렬화한다. 기록 버전이 다르면 409로 거절한다.
IaC 발견 건은 기존 담당자 필드를 단일 기준으로 사용하고, 기존 API로 변경했으면 sourceVersion으로 오래된 양식의 덮어쓰기를 막는다.
조치 저장과 담당자 동기화, 변경 이력은 같은 트랜잭션이다. 외부 티켓 번호는 받지 않는다.
사용자·시각·상태·담당자·메모를 내부 이력에 저장한다. 조회 자체는 기록을 생성하지 않는다.

## 로컬 검증

운영 DB와 분리한 PostgreSQL에 예시 이미지/경로/드리프트를 넣어 저장 및 재조회한다.
백엔드는 프론트보다 먼저 배포해야 하며 Flyway V71/V72를 적용해야 한다. IaC 재검사 연결에는 변경된 IaC 워커도 필요하다.
로컬 시연 주소는 http://127.0.0.1:5175/actions, API는 127.0.0.1:18082다. `logssey_actions_demo` DB만 사용한다.
검증은 시크릿 빈 스캔 예제 재생, IaC plan 예제의 실제 워커 분석, 기존 이미지 검사 산출물의 API 재입력으로 수행했다. 실제 AWS/GitHub 재수집이나 새 이미지 빌드를 실행한 증거와 구분한다.
이번 작업에서 운영 Re:Used 서비스·인프라, 배포 및 CI 설정은 변경하지 않았다. 시크릿 재검사 수정 e0ae330은 기존 별도 작업의 수정이며 로컬 검증을 위해 함께 반영했다.
