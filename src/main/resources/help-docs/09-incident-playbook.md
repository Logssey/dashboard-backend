# 침해사고 대응: 관리자가 먼저 확인할 것

Log4Shell이나 PHP 원격 코드 실행처럼 큰 취약점 사고가 터졌을 때, 관리자가 보통 확인하는 순서입니다. 항목마다 Logssey에서 볼 곳과 무엇을 보면 확인되는지(확인 기준)를 적었습니다. Logssey에 화면이 없는 일은 "Logssey 밖"으로 적었습니다. 단계는 합쳐서 볼 수 있지만 빼지 말고 모두 확인합니다.

## 확인 순서 요약
무엇이 터졌나 → 영향 범위 → 빠진 곳이 없나 → 실제로 뚫릴 수 있나 → 이미 뚫렸나 → 번지지 않게 막기 → 키·비밀 정리 → 계정·권한·설정 변경 확인 → 고치고 다시 확인 → 기록·보고

## 1. 무엇이 터졌나
- 확인할 것: 취약점 번호(CVE), 영향 받는 제품과 버전.
- Logssey에서 볼 곳: 취약점 관리 > Finding 목록의 "CVE 검색" 칸.
- 확인 기준: CVE 번호의 숫자 부분(예: 44228)으로 검색해 해당 패키지가 나오는지 봅니다.

## 2. 영향 범위
- 확인할 것: 어느 앱·이미지에 그 버전이 들어 있는지.
- Logssey에서 볼 곳: Finding 목록의 "심각도" 필터와 "배포 상태" 필터에서 "실행 중" 고르기.
- 확인 기준: 실행 중인 곳에 있으면 가장 먼저 처리합니다. 검색 결과가 없어도 안전하다는 뜻이 아닙니다. 스캔하지 않은 이미지는 목록에 나오지 않습니다.

## 3. 빠진 곳이 없나
- 확인할 것: 아직 스캔하지 않은 이미지나 레포.
- Logssey에서 볼 곳: 취약점 관리 > 워크로드의 "스캔 없음 · 불일치" 카드와 줄의 "스캔 요청", 스캔 화면의 "새 스캔".
- 확인 기준: "스캔한 digest와 일치"가 "실행 중 워크로드" 수와 같아질 때까지 스캔한 뒤 1번과 2번을 다시 봅니다.

## 4. 실제로 뚫릴 수 있나
- 확인할 것: 취약한 코드가 실제로 호출되는지, 바깥에서 닿는지.
- Logssey에서 볼 곳: Finding 상세의 "근거"(호출 경로)와 판정 상태, 인프라 보안 > IaC 보안의 "지금 열린 공격 경로".
- 확인 기준: 판정이 "도달 가능"이고 바깥에서 닿는 경로가 열려 있으면 가장 위험합니다. "미확인"이나 "사람 확인 필요"는 사람이 호출 경로를 직접 봅니다.

## 5. 이미 뚫렸나
- 확인할 것: 악용 시도, 이상한 프로그램 실행, 이상한 외부 접속.
- Logssey에서 볼 곳: 인프라 보안 > 런타임 보안의 "탐지 결과"와 "Sensor 상태".
- 확인 기준: 사고가 알려진 시점 이후의 탐지를 봅니다. "연결된 런타임 센서가 없어요"가 보이면 Logssey로는 확인할 수 없습니다.
- Logssey 밖: 웹 서버 접근 로그와 클라우드 감사 로그(AWS CloudTrail)를 확인합니다.

## 6. 번지지 않게 막기
- 확인할 것: 영향 받은 서버 격리, 바깥 접근 차단.
- Logssey 밖: Logssey는 탐지 전용이라 차단하지 않습니다. 보안 그룹이나 방화벽으로 막고 서버를 격리합니다.
- 확인 기준: 막은 뒤 IaC 보안의 "지금 점검"으로 4번의 공격 경로가 닫혔는지 다시 봅니다.

## 7. 키·비밀 정리
- 확인할 것: 뚫린 서버가 쓰던 키, 코드나 설정에 들어 있던 키.
- Logssey에서 볼 곳: 시크릿 > 키·노출 위치, 대응 관리, IaC 보안의 "State 속 실제 시크릿".
- 확인 기준: 교체가 필요한 키를 대응 건으로 만듭니다. 원격 코드 실행 사고라면 그 서버의 키는 모두 교체 대상으로 봅니다.

## 8. 계정·권한·설정 변경 확인
- 확인할 것: 새로 생긴 계정, 높아진 권한, 바뀐 설정.
- Logssey에서 볼 곳: 인프라 보안 > 컴플라이언스의 "새 점검" 결과, IaC 보안의 "실제 드리프트".
- 확인 기준: 사고 전 점검 결과와 비교해 새로 실패한 항목이나 새 드리프트가 있는지 봅니다.
- Logssey 밖: 신원·권한 화면은 아직 준비 중입니다. 계정·권한 변경 기록은 클라우드 콘솔에서 확인합니다.

## 9. 고치고 다시 확인
- 확인할 것: 패치나 버전 올리기가 실제로 반영됐는지.
- Logssey에서 볼 곳: Finding 상세의 "수정 버전"과 "업그레이드 제안", 배포 뒤 "새 스캔".
- 확인 기준: 새 스캔 뒤 해당 CVE Finding이 운영 중 이미지에서 사라졌는지 봅니다.

## 10. 기록·보고
- 확인할 것: 무엇을 확인했고 무엇을 했는지.
- Logssey에서 볼 곳: Finding 상세의 "판정 선택", "메모", "검토 저장", 시크릿 대응 관리, 컴플라이언스의 "감사 보고서".
- 확인 기준: 검토 이력과 대응 건에 남아 있는지 봅니다.
- Logssey 밖: 사내 보고를 합니다. 외부 신고(예: KISA 침해사고 신고)가 필요한지와 기한, 방법은 담당 부서와 확인합니다.

## 실제로 뚫렸는지 묻는 질문
도우미는 실제 탐지 결과나 서버 상태를 볼 수 없어서, 뚫렸는지 또는 영향이 있는지 알려 줄 수 없습니다. 이런 질문에는 5번(이미 뚫렸나)과 8번(계정·권한·설정 변경 확인)의 화면에서 직접 확인하도록 안내합니다.

## 사고 예시
- Log4Shell (Apache Log4j 원격 코드 실행): CVE-2021-44228, 후속 CVE-2021-45046. 4번의 "도달 가능" 여부, 5번 악용 흔적, 7번 서버 키 교체를 특히 봅니다.
- PHP 원격 코드 실행 (예: PHP-CGI 인자 주입 CVE-2024-4577): 해당 CVE 번호와 php 패키지로 검색합니다. 2번 운영 중 이미지, 4번 바깥에서 닿는 경로, 5번 악용 흔적을 특히 봅니다.
